# 后端开发技术文档（Go 版若依）

> 本文档基于 `server/` 目录实际代码梳理而成，作为后端二次开发时的统一约定。代码分层遵循「路由 → 处理器 → 服务 → 模型」的架构，配套 swagger 接口定义与通用工具包。

## 1. 项目概览

| 项目 | 说明 |
| --- | --- |
| 模块名 | `go-fin-server` |
| Go 版本 | `1.26.0`（见 `go.mod`） |
| Web 框架 | `gin` v1.12.0 |
| ORM | `gorm` v1.31.2（支持 `mysql` / `postgres` 双驱动） |
| 配置 | `spf13/viper`，配置文件 `configs/release.yaml` / `test.yaml` |
| 日志 | `zap` + `lumberjack` 轮转 |
| 缓存 | `go-redis` v9（支持多实例，默认名为 `master`） |
| 鉴权 | `golang-jwt/jwt/v5`，Token 存 Redis，支持注销 |
| 加密 | `rsatool`（RSA 公钥加密登录密码） |
| 验证码 | `base64Captcha` |
| 定时任务 | `robfig/cron/v3` + 自定义任务注册器 |
| 实时通讯 | WebSocket（聊天 + 在线用户） |
| 接口文档 | `swaggo/swag` + `gin-swagger`，Swagger 注解写在 Handler 上 |

### 启动方式

```bash
cd server
go run main.go -c release   # 使用 configs/release.yaml
go run main.go -c test      # 使用 configs/test.yaml
```

- 默认端口：`8080`（在 `release.yaml` 的 `server.port` 配置）。
- 启动流程：加载配置 → 初始化日志 → 创建上传目录 → 初始化 Redis → 初始化数据库 → 加载字典缓存 → 启动定时任务调度器 → 启动 WebSocket Hub → 注册路由 → 优雅启动/停止。

### 构建

```bash
cd server
go build -o server main.go
```

## 3. 分层架构与请求链路

一次接口请求的完整链路：

```
客户端请求
   │
   ▼
router 层（internal/router）        注册路由 + 挂载权限中间件
   │
   ▼
middleware 层（internal/middleware） JWT 鉴权 → 权限校验 → 操作日志 → 限流/签名校验
   │
   ▼
handler 层（internal/handler）      绑定请求参数 → 调用 service → 返回 response
   │
   ▼
service 层（internal/service）      业务逻辑编排，调用 model
   │
   ▼
model 层（internal/model）          GORM 模型 + 数据查询/写入
   │
   ▼
数据库（GORM 连接，默认 master）
```

**依赖方向（单向）：** `handler → service → model`，`router → handler`。各层职责单一，禁止跨层调用（如 handler 直接操作数据库）。

## 4. 各层编写规范

### 4.1 Model 层（`internal/model/`）

- 每个业务实体一个 `.go` 文件，文件名与表名对应，如 `sys_user.go` 对应表 `sys_user`。
- 定义 GORM 结构体，字段 tag 遵循以下约定：

```go
type SysUser struct {
	Id       uint64 `gorm:"column:id;primary_key" json:"id" description:"用户ID"`
	UserName string `gorm:"column:user_name" json:"userName" description:"用户名" binding:"required" err_msg:"用户名称 必填"`
	// ...
	BaseModel
}
```

| Tag | 用途 |
| --- | --- |
| `gorm:"column:xxx"` | 数据库列名映射，主键加 `primary_key`，默认值加 `default:'0'` |
| `json:"xxx"` | JSON 序列化字段名（后端统一驼峰） |
| `description:"xxx"` | 字段说明，同时作为前端字段注释依据 |
| `binding:"required"` | 校验规则（gin validator） |
| `err_msg:"xxx"` | 校验失败时的自定义错误消息（`api.ShouldBindError` 会读取） |

- 时间字段使用 `pkg/types.LocalTime`（自定义时间类型）。
- 关联关系通过 `gorm:"foreignKey:...;references:..."` 定义，如 `SysDept` 关联。
- **数据访问方法**直接定义在模型上（`func (c SysUser) SelectUserList(...)`），支持：
  - 分页查询：`SelectXxxList(conditions, sortConditions, pageNum, pageSize) ([]Model, int64, error)`
  - 列表查询：`SelectXxxAllList(conditions)`
  - 单条查询：`SelectXxxById(id)`
  - 新增/修改/删除：`InsertXxx` / `UpdateXxx` / `DeleteXxxByIds`
- 条件由上层传入 `map[string]interface{}`（key 为 `字段 = ?` 形式），配合 `query.Where(key, value)` 动态拼接。
- 分页使用 `pkg/utils.PageParse(pageNum, pageSize)` 计算 offset/limit。
- 每个模型必须实现 `TableName() string` 返回表名。
- **布尔字段约定（checkbox 字段）**：前端以复选框/开关表示的是/否字段（如角色的 `menu_check_strictly`、`dept_check_strictly`），模型字段统一用 `bool`，GORM 映射到 MySQL `BOOLEAN`（即 `tinyint(1)`），天然支持 `0/1` 存储；对应请求结构体（`api/system/sys_role.go` 的 `UpdateRoleRequest`）同样用 `bool`，直接接收前端布尔值，避免 `uint` 与 `true/false` 的绑定冲突（`Invalid type for field menuCheckStrictly, expected uint`）。相关树查询方法（`SelectMenuListByRoleId`、`SelectDeptListByRoleId`）参数也用 `bool`。

### 4.2 Service 层（`internal/service/`）

- 一个业务模块一个文件，结构体方法接收者为值类型：`type SysUserService struct{}`。
- Service 只做**业务编排**，数据访问委托给 Model；带数据权限的方法需接收当前登录用户。
- 方法命名以业务动词开头：`SelectXxxList` / `SelectXxxById` / `InsertXxx` / `UpdateXxx` / `DeleteXxxByIds`。
- 在 `internal/service/init.go` 的 `Services` 结构体中注册，Handler 通过 `s.Services.SysXxxService` 访问：

```go
type Services struct {
	TokenService      common.TokenService
	SysUserService    system.SysUserService
	SysRoleService    system.SysRoleService
	// ... 每新增一个服务在此登记
}
```

### 4.3 Handler 层（`internal/handler/`）

- 每个业务模块一个结构体 + `NewXxxHandler()` 构造方法：

```go
type UserHandler struct {
	Services service.Services
	Api      api.Api
}

func NewUserHandler() *UserHandler {
	return &UserHandler{}
}
```

- 每个接口一个方法，统一范式：
  1. `response.SetOperTitle(c, "操作名称")`：记录操作日志标题。
  2. 用 `s.Api.Xxx.XXXRequest`（swagger 请求结构体）+ `api.ShouldBindError(c, &req)` 或 `api.ShouldBindUriError(c, &req)` 绑定参数。
  3. 调用 `s.Services.SysXxxService.xxx()`。
  4. 成功 `response.PageData(c, data, total)` 或 `response.Data(c, data)`，失败 `response.Error(c, err.Error())`。
- 在方法上方编写 **Swagger 注解**（`@Summary` / `@Tags` / `@Param` / `@Success` / `@Router` / `@Security BearerAuth`），供 swagger 文档生成。

### 4.4 Router 层（`internal/router/`）

- 每个模块一个 `SetupXxxRoutes(g *gin.RouterGroup)` 函数。
- 挂载权限中间件：`middleware.PermissionMiddleware("system:user:list")`，权限标识与前端菜单权限一致。
- 路由方法约定：查询 GET、新增 POST、修改 PUT、删除 DELETE（批量删除用 `DELETE /:ids`）。
- 路由需要在 `internal/router/router.go` 中统一注册（按系统/监控/工具模块组织）。

### 4.5 API 定义层（`api/`）

- 每个模块一个文件（如 `api/system/sys_user.go`），定义请求结构体，供 Handler 绑定与 Swagger 使用。
- 命名约定：`XxxListRequest`（列表查询）、`XxxAddRequest` / `XxxEditRequest`（增改）、`XxxIdUriRequest`（URI 参数）、`XxxDeleteRequest`。
- 分页参数：`pageNum` / `pageSize`（query 参数），并支持 `Sort` 排序字段。

## 5. 统一响应规范（`internal/response/`）

| 方法 | 返回结构 | 适用 |
| --- | --- | --- |
| `response.Data(c, data)` | `{"code":200,"msg":"success","data":...}` | 普通查询/操作 |
| `response.DataMsg(c, data, msg)` | `{"code":200,"msg":"自定义","data":...}` | 带自定义消息 |
| `response.DataExpand(c, data, other)` | 在 Data 基础上合并其他字段 | 扩展字段 |
| `response.PageData(c, data, total)` | `{"code":200,"msg":"success","rows":...,"total":...}` | **分页列表**（前端 `TableDataInfo` 对应） |
| `response.Error(c, msg)` | `{"code":400,"msg":"...","data":null}` | 业务错误 |
| `response.ErrorCode(c, code, msg)` | 自定义错误码 | 特殊错误 |
| `response.SetOperTitle(c, title)` | — | 操作日志标题 |

> 约定：业务成功统一 `code=200`，业务失败 `code=400`。HTTP 状态码始终为 200，错误通过 body 的 `code/msg` 表达（前端 `utils/http` 拦截器据此判断）。

## 6. 鉴权与权限

- **JWT 中间件**（`internal/middleware/jwt_middleware.go`）：校验请求头 `Authorization: Bearer {token}`，校验通过后把登录用户写入 `c.Set("loginUser", ...)`，Handler 通过 `c.MustGet("loginUser").(*model.LoginUser)` 获取。
- **权限中间件**（`internal/middleware/permission_middleware.go`）：`PermissionMiddleware("system:user:list")`，校验当前用户是否拥有该权限标识，未授权返回 403。
- 未登录 / Token 失效返回 401，前端自动登出。
- 数据权限在 Service/Model 层处理：带数据权限的查询方法接收当前登录用户（如 `SelectDataScopeUserList(..., user model.SysUser)`），按表特判。

### 6.1 会话有效期：滑动续期 + 1 天上限

解决"登录后无操作自动掉线"问题。核心文件 `internal/service/common/token.go`、`internal/middleware/jwt_middleware.go`。

- **滑动续期**：JWT 中间件每次认证通过后调用 `tokenService.VerifyToken(loginUser)` 续期——当会话剩余有效期不足 **20 分钟**时才刷新（避免每次请求都写 Redis）。前端登录后每 30s 心跳调用 `/getInfo`，因此打开页面即有持续请求，会话不会因"无操作"而过期。
- **1 天硬上限**：`LoginTime` 作为会话起点（登录时刻，不可变，也用于在线用户监控展示），`VerifyToken` 内计算 `deadline = LoginTime + 24h`；续期后绝对过期时刻为 `min(now + expiration_time, deadline)`，**到达 24h 后返回 401，强制重新登录**。即：活跃会话最长存活 1 天，不因续期无限延长。
- **Redis TTL 用真实剩余时长**：`RefreshToken` 中 `TTL = expireTime - now`（此前固定为 `expiration_time`，会在接近上限时错误超发）；且不再覆盖 `LoginTime`，保留原始登录时刻。
- **配置项**：`configs/release.yaml` 的 `jwt.expiration_time`（分钟）为**续期滑动窗口**（已从 10 调到 100），仅决定续期频率，不决定会话总时长；总时长上限固定为 1 天（代码内常量 `24*60*60`）。

```
登录(LoginTime=T0)         活动/心跳持续续期               T0+24h
  ├───────────────────────────────●──────────────────────────●
  每请求剩余<20min则续期到 min(T+窗口, T0+24h)    到点强制 401 重登
```

> 说明：彻底空闲且页面未打开、无任何请求时，最长空闲 `expiration_time`（100 分钟）后失效。

## 7. 中间件（`internal/middleware/`）

| 中间件 | 作用 |
| --- | --- |
| `jwt_middleware.go` | JWT 鉴权，注入 loginUser，并通过 `VerifyToken` 滑动续期（1 天上限） |
| `permission_middleware.go` | 接口访问权限（权限标识） |
| `operation_log_middleware.go` | 操作日志记录 |
| `rate_limit_middleware.go` | 接口限流（`juju/ratelimit`） |
| `sign_verification_middleware.go` | 请求参数 sign 签名校验 |
| `cors_middleware.go` | 跨域处理 |
| `error_log_middleware.go` | 错误日志记录 |

新增通用逻辑优先以中间件形式接入，而不是散落在 Handler 中。

## 8. 配置管理（`internal/config/`）

- `viper` 加载 `configs/release.yaml`（或 `test.yaml`），全局配置对象 `config.GlobalConfig`。
- 配置项：
  - `server.port` / `server.host`
  - `database_list`：支持多个数据库连接，默认连接名 `master`，驱动支持 `mysql` / `postgres`
  - `redis_list`：支持多个 Redis 实例，默认 `master`
  - `log`：日志级别 / 格式 / 目录 / 轮转参数
  - `rsa.public_key` / `rsa.private_key`：登录密码 RSA 加解密密钥
- 数据库连接通过 `db.DBConnections["master"]` 访问；Redis 通过 `db.RedisConnections["master"]` 访问。

## 10. 新增一个业务模块的完整流程（Checklist）

假设新增「客户管理」（customer）模块：

1. **Model**：在 `internal/model/` 新增 `customer.go`，定义 `Customer` 结构体（含 `BaseModel`）与 `TableName()`，编写查询方法。
2. **Service**：在 `internal/service/` 新增 `customer.go`，定义 `CustomerService`，并在 `internal/service/init.go` 的 `Services` 中注册。
3. **Handler**：在 `internal/handler/` 新增 `customer.go`，定义 `CustomerHandler` + `NewCustomerHandler()`，编写增删改查方法（含 Swagger 注解）。
4. **API 定义**：在 `api/` 新增 `customer.go`，定义请求结构体，并注册到 `api/init.go` 的 `Api` 结构体。
5. **Router**：在 `internal/router/` 新增 `customer.go`，定义 `SetupCustomerRoutes`，挂载权限中间件（如 `system:customer:list`），并在 `router.go` 注册。
6. **验证**：`go build` 编译通过；启动后访问 `http://localhost:8080/swagger/index.html` 查看接口。

> 详细代码示例见《开发操作示例.md》。
